# 🥞 Implement Queue using Stacks — LeetCode #232

## 📌 Problem

Implement a FIFO Queue using only Stack operations.

The queue should support:

```text
push(x)
pop()
peek()
empty()
```

### Queue follows:

```text
FIFO → First In, First Out
```

### Stack follows:

```text
LIFO → Last In, First Out
```

The challenge is to use two stacks to make the stack behavior work like a queue.

---

# 🧠 Brute Force Thought Process

A queue needs:

```text
First element inserted
        ↓
First element removed
```

But a stack gives:

```text
Last element inserted
        ↓
First element removed
```

So if we use only one stack, the newest element is always on top.

We need a way to reverse the order.

That's why we use **two stacks**:

```text
InputStack
OutputStack
```

---

# 🚀 Approach — Two Stacks

We use:

```text
InputStack  → stores newly pushed elements

OutputStack → provides queue order for pop/peek
```

The important observation is:

> When we transfer all elements from `InputStack` to `OutputStack`, their order gets reversed.

For example:

```text
push(1)
push(2)
push(3)
```

### InputStack

```text
Top
 ↓
3
2
1
```

Transfer everything:

```text
InputStack              OutputStack

   3                         1
   2          →              2
   1                         3
```

Now `1` is on top of `OutputStack`.

Therefore:

```text
pop() → 1
```

which is exactly the Queue behavior.

---

# 🔄 How Each Operation Works

## 1️⃣ push(x)

Simply push into `InputStack`.

```java
InputStack.push(x);
```

Example:

```text
push(1)
push(2)
push(3)
```

Result:

```text
InputStack

3 ← top
2
1
```

No transfer is required during `push()`.

---

## 2️⃣ pop()

First check:

```java
if(OutputStack.isEmpty())
```

If `OutputStack` is empty, transfer everything from `InputStack`.

```java
while(!InputStack.isEmpty()){
    OutputStack.push(InputStack.pop());
}
```

Then:

```java
return OutputStack.pop();
```

### Example

Initially:

```text
InputStack       OutputStack

3
2
1
```

Transfer:

```text
InputStack       OutputStack

                 1 ← top
                 2
                 3
```

Then:

```text
pop() → 1
```

---

# 3️⃣ peek()

`peek()` is almost the same as `pop()`.

The only difference is:

```java
OutputStack.peek()
```

instead of:

```java
OutputStack.pop()
```

So the element is viewed but not removed.

```java
if(OutputStack.isEmpty()) {
    while(!InputStack.isEmpty()) {
        OutputStack.push(InputStack.pop());
    }
}

return OutputStack.peek();
```

---

# 4️⃣ empty()

The queue is empty only when **both stacks are empty**.

```java
if(OutputStack.isEmpty() && InputStack.isEmpty())
    return true;

return false;
```

It can also be written more simply:

```java
return InputStack.isEmpty() && OutputStack.isEmpty();
```

# 💡 Important Observation

The most important idea is:

> **Transfer elements only when `OutputStack` is empty.**

Do NOT transfer elements on every `pop()`.

Why?

Suppose:

```text
InputStack:

5
4
3
2
1
```

We transfer once:

```text
OutputStack:

1
2
3
4
5
```

Now we can perform:

```text
pop() → 1
pop() → 2
pop() → 3
pop() → 4
pop() → 5
```

without transferring again.

This is what gives us **amortized O(1)** complexity.

# 🔧 Your Approach

Your implementation follows:

```text
push()
   ↓
InputStack.push(x)


pop()
   ↓
Is OutputStack empty?
   ↓
Yes → Transfer Input → Output
   ↓
OutputStack.pop()


peek()
   ↓
Is OutputStack empty?
   ↓
Yes → Transfer Input → Output
   ↓
OutputStack.peek()


empty()
   ↓
Both stacks empty?
```

This is the standard optimal approach.

# 🔧 Your Code

```java
class MyQueue {

    Stack<Integer> InputStack;
    Stack<Integer> OutputStack;

    public MyQueue() {
        InputStack = new Stack<>();
        OutputStack = new Stack<>();
    }

    public void push(int x) {
        InputStack.push(x);
    }

    public int pop() {

        if(OutputStack.isEmpty()) {
            while(!InputStack.isEmpty()) {
                OutputStack.push(InputStack.pop());
            }
        }

        return OutputStack.pop();
    }

    public int peek() {

        if(OutputStack.isEmpty()) {
            while(!InputStack.isEmpty()) {
                OutputStack.push(InputStack.pop());
            }
        }

        return OutputStack.peek();
    }

    public boolean empty() {

        if(OutputStack.isEmpty() && InputStack.isEmpty())
            return true;

        return false;
    }
}
```

# 🔧 Cleaner Version

The logic remains exactly the same, but we can extract the transfer logic into a helper method.

```java
class MyQueue {

    Stack<Integer> inputStack;
    Stack<Integer> outputStack;

    public MyQueue() {
        inputStack = new Stack<>();
        outputStack = new Stack<>();
    }

    public void push(int x) {
        inputStack.push(x);
    }

    public void moveElements() {

        if(outputStack.isEmpty()) {
            while(!inputStack.isEmpty()) {
                outputStack.push(inputStack.pop());
            }
        }
    }

    public int pop() {
        moveElements();
        return outputStack.pop();
    }

    public int peek() {
        moveElements();
        return outputStack.peek();
    }

    public boolean empty() {
        return inputStack.isEmpty() && outputStack.isEmpty();
    }
}
```

The helper makes the main operations easier to read.

# 🧠 Why Do We Need Two Stacks?

Think of it as a reversal mechanism.

Suppose:

```text
InputStack

3
2
1
```

Stack pops in this order:

```text
3 → 2 → 1
```

After transferring:

```text
OutputStack

1
2
3
```

Now it pops in:

```text
1 → 2 → 3
```

Therefore:

```text
Stack
LIFO
 ↓
Reverse
 ↓
Queue
FIFO
```

# ⏱️ Complexity

| Operation | Complexity |
|---|---:|
| `push()` | O(1) |
| `pop()` | Amortized O(1) |
| `peek()` | Amortized O(1) |
| `empty()` | O(1) |

### Why is `pop()` amortized O(1)?

At first glance, this looks like:

```java
while(!InputStack.isEmpty())
```

which is `O(n)`.

But each element can be transferred from `InputStack` to `OutputStack` **only once** before it is popped.

Example:

```text
1 → transferred once
2 → transferred once
3 → transferred once
...
```

So across many operations, the total transfer work is linear.

Therefore:

```text
Amortized = O(1)
```

---

# 💾 Space Complexity

We store every queue element in one of the two stacks.

```text
Space = O(n)
```

where `n` is the number of elements in the queue.

# ⚠️ Common Mistakes

### 1. Moving elements every time

Don't do:

```java
while(!InputStack.isEmpty()) {
    OutputStack.push(InputStack.pop());
}
```

on every `pop()`.

Only transfer when:

```java
OutputStack.isEmpty()
```

---

### 2. Using `pop()` inside `peek()`

`peek()` should not remove the element.

Wrong:

```java
return OutputStack.pop();
```

Correct:

```java
return OutputStack.peek();
```

---

### 3. Checking only one stack in `empty()`

Wrong:

```java
return OutputStack.isEmpty();
```

`InputStack` might still contain elements.

Correct:

```java
return InputStack.isEmpty() && OutputStack.isEmpty();
```

# 🎯 Interview Explanation

If the interviewer asks:

> "How did you implement a queue using two stacks?"

You can say:

> "I maintain two stacks. The input stack stores newly inserted elements, while the output stack provides elements in queue order. Whenever I need to pop or peek and the output stack is empty, I transfer all elements from the input stack to the output stack. This reverses their order and makes the oldest element available at the top. I only perform this transfer when necessary, giving amortized O(1) time for pop and peek."

# 🔥 Final Takeaway

Remember this one line:

> **Input stack receives elements; Output stack serves elements. Transfer only when OutputStack is empty.**

```text
push
  ↓
InputStack


pop / peek
  ↓
OutputStack empty?
  ↓
Yes
  ↓
Transfer Input → Output
  ↓
Use OutputStack
```

### 🧠 Memory Trick

```text
Input  = New elements
Output = Oldest elements
```

The moment you understand this, **LeetCode #232 becomes a very easy stack/queue pattern to recognize.**
